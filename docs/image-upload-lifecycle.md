# 评论图片生命周期

适用 Halo 2.26.0。使用本插件图片上传功能时，需要同时更新服务端插件和评论组件；不使用受管图片的自建组件无需接入提交凭证。没有新增管理页、管理接口或公开删除接口。

## 数据保留

| 数据 | 用途和回收方式 |
| --- | --- |
| `CommentUpload` | 临时上传和未完成事务。成功关联后将长期关系写入 Attachment，确认后删除该上传记录。未提交图片保留 24 小时，附件实际删除后删除记录。 |
| `CommentSubmission` | 服务端签发的提交凭证及幂等结果。24 小时内允许首次提交；到期后再保留 1 小时，然后回收 ISSUED、BOUND、FAILED 记录。仍有上传依赖它时推迟回收。 |
| Attachment 标签和注解 | 保存上传标记、图片 URL、目标 Comment/Reply 类型和名称。关联与附件共同存在，不再额外保存永久上传 Extension。 |
| Comment/Reply 标签 | 图片引用路径的摘要索引，用于查询仍被其他评论引用的图片。评论内容改变时更新，随评论删除。 |
| 结果不明确的事务 | 保留核对依据，不自动删除图片；超过确认阶段后停止逐条周期轮询。 |

正常事务记录规模取决于近期上传、提交量，而非历史累计图片数。未确认的异常仍可能累积，因此这不是对任意异常或恶意流量的绝对容量上限。

## 上传、提交及重放保护

1. 选图、粘贴和拖放先在浏览器预览，提交时上传。每个编辑器使用随机 256 位草稿凭证；服务端保存其 SHA-256 摘要及认证用户名。
2. 上传前创建 CommentUpload，调用 Halo AttachmentService 的 `beforeCreating` 写入附件专属标记及 `attachment-manager` finalizer。附件创建返回后立即持久化其名称，再获取永久链接；链接生成失败不会丢失附件身份。返回 `{ uploadId, url, expiresAt }[]`。
3. 浏览器通过 `POST /apis/api.commentwidget.halo.run/v1alpha1/submissions` 申请提交编号。必须持有尚可提交的草稿图片；每草稿最多保留 20 个提交编号。编号和有效期由服务端生成、持久化。
4. 原评论/回复 POST 携带 `X-Comment-Upload-Token`、`X-Comment-Submission` 和 `X-Comment-Uploads`。认证完成后的 `AfterSecurityWebFilter` 检查凭证、图片归属、提交有效期和正文，再用资源版本检查将 ISSUED 改为 PREPARING、占用图片，进入 PROCESSING。
5. 读取有效成功响应并核实数据库中的 Comment/Reply 后，先保存目标恢复依据，再逐张绑定，最终标记提交成功。后台把长期关系转存附件，删除临时上传记录。上传绑定事件和提交成功事件都会触发回收，避免二者落盘顺序造成延迟。同一提交的前台绑定和后台恢复使用固定数量的分段锁串行执行，避免锁记录随提交数量增长；遇到资源版本冲突时重新读取并重试；已绑定到同一评论的记录直接视为成功。中途失败保留上传记录供重试。
6. 已确认的 400/401/403/404/413/422/429 失败释放图片占用，允许使用新的服务端编号重试。网络断开、取消、5xx 或无法核实的响应保持未知，不能据此删图。
7. 浏览器重试先查询提交状态：BOUND 恢复成功；ISSUED 可复用同一编号；FAILED 可申请新编号；未知结果停止重发。查不到或已过期的编号不会重新创建记录。

即使上传记录已经压缩删除，过滤器仍先校验携带的提交编号，不能因正文查不到临时记录而绕回普通评论分支。编号删除后，旧请求返回 404/410，不会变成新提交。已绑定的受管图片也不能去掉提交头后重新认领。

### 原评论接口兼容性

| 调用方式 | 接入要求 |
| --- | --- |
| 关闭上传、纯文字评论或回复 | 沿用 Halo 原接口，不申请提交编号，也不创建上传事务记录。 |
| 自建组件使用外部图床或历史非受管附件 | 沿用 Halo 原接口，无需上传请求头。 |
| 自建组件使用本插件上传的图片 | 申请提交编号，并携带上述三个上传请求头。 |
| 引用已有受管图片，或携带过期的提交编号 | 仍检查归属和有效期；移除请求头、关闭上传不能绕过保护。 |

过滤器从当前请求的 Halo 应用上下文获取实际的 JSON 解码器，沿用其解析配置和内存上限，不再另设 1 MiB 请求限制。JSON 语法或大小错误沿用框架的 `ServerWebInputException` 映射；不支持的媒体类型交回 Halo 处理。原始请求字节、请求头保留，具体字段、权限和评论业务校验仍由 Halo 执行；不再把下游普通接口的异常统一改写为上传错误。

为了发现未携带凭证却引用受管图片的请求，仍需对原评论/回复 JSON 正文做一次检查，关闭上传也保留这项检查。无提交编号且正文没有图片时，不进入上传生命周期服务、不查询上传记录；有图片时按索引检查是否受管，普通外部图片不创建事务。上传配置关闭的是新增上传能力，不会解除已有图片的归属保护。

普通文字、历史非受管附件和外部图片仍使用原评论接口。图片引用路径采用保守匹配：绝对链接和根相对链接可匹配同一路径；不同域名恰好使用同一路径时也可能被视为引用，以避免误删。

## 删除及大站调度

- `approved=false` 是待审核/取消审核，保留图片。只有实际删除 Comment/Reply 才安排图片回收，默认延迟 1 小时。主评论删除后，由 Halo 级联删除回复。
- 正常删除事件通过 Attachment 的目标标签定位图片，不再扫描所有上传记录。实际删除仍调用 Halo 的 Attachment 删除流程，存储文件由 Halo finalizer 处理。
- 删除前查询 Comment/Reply 的引用标签。其他评论仍引用时保留图片；引用被移除后，待清理任务再次检查。
- 健康的已绑定附件不挂逐条定时任务。只有临时事务和待删除附件需要定时重试；待删除附件可按标签在启动时恢复。
- 后台单线程按名称游标分批读取，每秒执行一轮，每类资源每轮最多 100 条。启动时分批构建 Comment/Reply 引用索引，构建完成前禁止自动删图。
- 附件兜底巡检只扫描有上传标记的附件，每批 100 条；一轮结束后等待 24 小时再扫描。它覆盖漏掉的删除事件和关联迁移恢复，不在每张图片上设置固定轮询。大站一轮扫描需要更多时间。
- 事件路径每次最多处理同一目标下的 100 个关联附件；超出部分由兜底巡检覆盖。正常评论组件的草稿图片上限为 20。

保留时间是最短期限；重启后的索引构建、并发冲突或存储故障可能延迟实际清理。图片已在存储侧消失时，上传记录可以直接回收，无需继续等待引用消失。

## 安全和兼容边界

- 上传使用 Halo/Spring 已解析的客户端地址限流，每分钟 10 次请求。插件不自行解析转发头，也没有代理 IP 配置项；代理头的信任与客户端地址解析沿用 Halo 部署的 HTTP 服务配置。限流缓存最多 10000 个地址，空闲 10 分钟的记录在后续请求时清理，达到容量时拒绝新地址，不能通过挤出活跃地址重置额度。
- 在解析 multipart 前验证草稿凭证与上传权限；复用 Halo 的 multipart 解析配置，在完成、失败、取消后清理临时 part。插件不额外设置文件 part 数量或大小上限。同一草稿最多 20 条临时上传记录，这是防止临时数据堆积的配额，与存储策略的文件规格配置分开。
- 文件大小、类型及其他文件规格交由 Halo 所选存储策略的附件处理器决定。插件直接将原始 FilePart 交给 AttachmentService.upload，不解码图片、不更改文件名和 MIME 类型、不设置像素或动画帧数上限。前端文件选择器使用 image/* 作为图片选择提示，不设置格式白名单或文件大小限制。
- 前台根据上传开关和匿名权限启用选图、粘贴及拖放，后台复用的编辑器默认禁用本地文件上传。提交期间锁定编辑器，等待评论请求结束后解锁；成功清空草稿时同时清空撤销历史、释放 blob URL。
- 草稿凭证、认证用户名共同验证所有权；图片 URL、资源名称、邮箱和 IP 均不能单独授权认领或删除。
- 历史未受管附件不参与自动清理。旧实现的 BOUND 上传记录会迁移关联后删除；旧 DELETED 记录会删除；未知记录保持保留。
- 兼容已有内部永久保留标记，将其转存附件注解；没有额外管理页面或入口。
- 受管图片不应直接复用于文章、页面或第三方插件，应独立上传附件。插件只跟踪 Comment/Reply 图片引用，不能证明任意第三方资源或站外内容没有引用。
- 公共附件链接不等于私有访问控制。此功能不改变附件访问权限。
- Halo 存储处理器写文件与创建 Attachment 不在同一事务。如果文件写入后、附件创建前进程崩溃，插件不能安全定位物理孤儿文件，只保留未确认记录；需要存储侧核对能力。
- 无目标依据的 UNKNOWN、被中断的 PREPARING、无法确认附件的 UPLOADING 不按 TTL 直接释放。已确认附件身份但永久链接生成失败的上传可在 24 小时到期后回收，删除仍验证归属标记。停止频繁轮询后仍保留记录；后续附件事件可恢复晚到的上传。
- 浏览器刷新会丢失本地草稿及重试上下文，不改变服务端保护。客户端不自动用新编号重放失效的旧提交。
- 草稿配额和 IP 限流基于单 Halo 实例。跨实例的全局配额不在本实现范围。

## 代码职责与重构验证

- `UploadLifecycleService` 保留提交签发、占用和绑定的统一入口；`UploadReferenceIndex` 管理评论/回复引用索引，`UploadAttachmentService` 管理附件关联压缩与延迟回收。
- `UploadSubmissionFilter` 负责请求识别、解码与转发；`UploadSubmissionResponse` 负责响应校验和提交结果记录。正常结束、异常和取消仍分别处理。
- `UploadMediaEndpoint` 复用 Halo multipart 解析并编排串行上传，将原始文件交给 Halo 附件服务。`UploadRetries` 保持完整读改写重试，绑定时仍处于原分段锁内。
- 前端 `editor-upload.ts` 接入选择/粘贴/拖放，`uploaded-images.ts` 管理预览与节点替换，`upload-api.ts` 负责上传请求，`UploadSession` 管理提交凭证与重试恢复。`SubmissionDetail` 明确表单事件边界。
- 重构回归：55 项后端测试、16 项前端测试、前端类型检查和构建通过。新增用例覆盖取消后保留未知结果、改变正文后禁止重放，以及纯文字请求不申请/携带上传凭证。
- Chrome 使用实际 Halo 页面验证图片边界输入、侧边缩放、只读上传禁用、清空后的撤销状态，以及合成粘贴/拖放事件产生本地预览；没有提交测试评论。本轮未重跑操作系统文件选择器到评论提交的完整链路。


## 文件规格由 Halo 决定

- Halo 的 `DefaultAttachmentService.upload` 根据所选策略调用 `AttachmentHandler`；本地存储的 `LocalAttachmentUploadHandler.validateFile` 读取策略中的 `maxFileSize` 和 `allowedFileTypes`。其他存储策略由对应处理器实现校验，插件不覆盖这些规则。
- 已删除插件的文件大小、四种图片格式、像素、动画帧数限制，以及 TwelveMonkeys 依赖；不再将文件整体缓存在内存中解码。前端与 multipart 均不再设置每次 10 个文件的上限。
- 仍保留同一草稿 20 条临时上传记录、提交凭证配额、请求限流、所有权校验及延迟清理。这些约束管理临时资源与提交状态，不替代附件策略的文件规格校验。
- 本轮 55 项后端测试和 16 项前端测试通过，类型检查与构建通过。新增真实 multipart 解析用例覆盖 11 MiB AVIF 原样传给模拟附件服务、11 个文件 part、继承宿主 multipart 上限、存储策略错误透传，以及成功、失败、取消后的临时文件清理。
- 新构建已加载到本地 Halo。Chrome 合成粘贴验证超过 10 MiB 的 SVG 和一次 11 张图片可进入预览，之后刷新清除测试内容；本轮没有执行真实存储策略上传到评论提交的完整链路。


## 上传失败与剪贴板恢复

- multipart 请求解析成功后，上传接口按文件顺序返回结果数组。成功项仍包含 `uploadId`、`url`、`expiresAt`；失败项包含 `error.status` 和 `error.message`。单个文件失败不丢弃其他成功项；权限、限流、配置或 multipart 解析阶段的整体失败仍使用 HTTP 错误响应。
- 前端先写回所有成功项，再提示失败原因。再次提交只上传仍为本地状态的图片，同一 blob 的多个副本只上传一次。20 条草稿配额保持不变；超过配额时，用户可移除未成功的图片后提交已经上传的部分。
- Halo 明确报告文件大小、类型或扩展名不符合存储策略时，后端检查上传记录仍为 UPLOADING、没有附件关联、也找不到带该记录标记的 Attachment，再删除该失败记录释放配额。仅在存储上传阶段处理这些确定拒绝；普通 400、未知错误和取消不据此删除恢复依据。
- 图片剪切粘贴通过当前编辑器会话的映射恢复 File 或上传编号；嵌套结构、尺寸和文本保留，不信任外部 HTML 中的上传属性。成功上传后，旧 blob 地址和附件 URL 均能恢复到同一关联；清空表单或销毁编辑器会清除映射。
- 新增回归覆盖混合上传结果、20 张成功后配额拒绝、连续拒绝释放配额、已有附件时禁止丢弃记录、未知错误保留，以及本地/已上传图片剪贴板恢复和伪造属性。60 项后端测试、23 项前端测试通过。
- Chrome 在新构建上验证本地图片剪切粘贴保留原 File；模拟部分失败响应后，两轮上传文件数依次为 2 和 1，已上传图片剪切粘贴保留原编号。测试请求未提交真实评论，测试结束刷新恢复页面。


### 撤销和重做后的上传恢复

上传前会根据当前编辑会话中的成功记录修复历史恢复出的本地图片节点，再收集真正需要上传的文件。恢复原附件 URL 和上传编号时保留尺寸、标记和编辑历史，不增加撤销步骤；没有成功上传记录的本地文件仍正常上传。
